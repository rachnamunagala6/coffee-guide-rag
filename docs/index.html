The coffee guide, under the hood

RAG with Elasticsearch

How hybrid retrieval finds the right passages and how Claude turns them into cited answers

This deck walks through the technical design of the coffee guide, a retrieval-augmented generation system. The focus is the retrieval side: how documents are chunked and indexed in Elasticsearch, how BM25 and vector search run side by side, how their results are fused, and how the retrieved passages become a grounded, cited answer.

Each chunk is stored once with both its text and its vector, so one Elasticsearch index serves keyword and vector search.

Indexing runs offline: Markdown guides are split at headings, each chunk is embedded into a 384-dimensional vector, and text plus vector are bulk-indexed. At query time the question, plus the previous question for follow-ups, goes to two retrievers in parallel, BM25 and kNN, each returning its top 20. Reciprocal rank fusion merges them, the top five chunks are numbered into the prompt, and Claude answers with citations.

Chunking: one topic per chunk

Split at Markdown headings, not fixed word counts, so a chunk never mixes the end of one recipe with the start of the next.

Prepend the heading path to the text, so both BM25 and the embedding see the topic.

Fallback for long sections: 250-word windows with 50 words of overlap.

Result: 7 guides become 55 chunks of 26 to 179 words.

One indexed document

{
  "title": "How to Brew: Step-by-Step Methods",
  "section": "French press",
  "text": "How to Brew: Step-by-Step Methods
    - French press\n**You need:** coarse
    grind, about 1:15 ratio...",
  "source": "docs/06-brew-methods.md",
  "chunk_id": 3,
  "embedding": [0.021, -0.087, ...384]
}

Chunking has the biggest effect on retrieval quality. The first version used fixed 300-word windows, which can cut across topics: one chunk ends up half drip machine and half pour-over, its embedding sits between the two, and its citation points at neither cleanly. Splitting on headings makes each chunk self-contained and makes the citation meaningful: a section name the user recognizes. The heading path is prepended to the text so a query like "french press" matches the chunk even if the body never repeats the phrase. The embedding values shown are illustrative.

The index mapping

"properties": {
  "text":    { "type": "text", "analyzer": "english" },
  "title":   { "type": "text", "analyzer": "english" },
  "section": { "type": "text", "analyzer": "english",
             "fields": { "raw": { "type": "keyword" } } },
  "source":  { "type": "keyword" },
  "chunk_id": { "type": "integer" },
  "embedding": {
    "type": "dense_vector", "dims": 384,
    "index": true, "similarity": "cosine"
  }
}

Two structures, one document. Text fields go into an inverted index for BM25; the vector goes into an HNSW graph for kNN.

english analyzer stems words and drops stop words, so “grinding” matches “grind”.

source as keyword allows exact-match deletes when a file is re-ingested.

dims is fixed at creation: a new embedding model means rebuilding with --recreate.

The mapping is created explicitly rather than letting Elasticsearch guess field types. The text, title and section fields use the English analyzer for stemming. Section also has a keyword sub-field for exact filtering or aggregations. The dense_vector field is indexed, which builds an HNSW graph for approximate nearest-neighbour search, using cosine similarity. Because the embeddings are normalized to unit length, cosine and dot product give the same ranking.

Embeddings: meaning as 384 numbers

384

dimensions per chunk, from all-MiniLM-L6-v2

Runs locally through sentence-transformers on a CPU: a 90 MB model, loaded once and cached.

Normalized to unit length, so cosine similarity and dot product rank results the same way.

Same model for chunks and questions. Vectors from different models live in different spaces and can’t be compared.

Short input window (256 tokens) is one more reason to keep chunks small.

The embedding model maps text with similar meaning to nearby points, which is what lets "tastes like vinegar" land near the section about sour coffee. MiniLM is a deliberate starting choice: small, fast and free. Stronger options are bge-small or bge-base from the same library, or Elastic's own inference endpoints, which move embedding inside the cluster. Any change of model requires re-indexing, since dims and vector space change.

Ingestion is idempotent

For each file

  1. Chunk it by heading
  2. Delete its old chunks by source
  3. Embed all chunks in one batch
  4. Bulk index with deterministic IDs
  5. Refresh so they’re searchable

Re-running never duplicates, and an edited file leaves no stale chunks behind.

es.delete_by_query(index=INDEX,
    query={"term": {"source": source}})

vectors = embed([c["text"] for c in chunks])

actions = [{
  "_index": INDEX,
  "_id": sha1(f"{source}:{i}"),
  "_source": {**chunk, "source": source,
              "chunk_id": i, "embedding": vec},
} for i, (chunk, vec) in enumerate(...)]

helpers.bulk(es, actions)

Delete-then-insert per file handles the case where an edited file now has fewer chunks: deterministic IDs alone would leave the old tail behind. Batching the embeddings is much faster than embedding one chunk at a time, and the bulk helper sends all of a file's documents in one request. The code is simplified from ingest.py: sha1 stands for hashlib.sha1 of the string, hex-encoded.

Two retrievers, side by side

BM25 keyword search

es.search(index=INDEX, size=20,
  query={"multi_match": {
    "query": question,
    "fields": ["text",
              "section^2", "title"]
  }},
  source_excludes=["embedding"])

Stemmed term matching, with heading matches weighted double. Strong on names and numbers like “AeroPress” or “1:16”.

kNN vector search

es.search(index=INDEX, size=20,
  knn={
    "field": "embedding",
    "query_vector": embed([question])[0],
    "k": 20, "num_candidates": 100
  },
  source_excludes=["embedding"])

Approximate nearest neighbours on the HNSW graph. Strong on paraphrase: “tastes like vinegar” finds the sour-coffee section.

Both queries hit the same index and each returns its top 20 hits. num_candidates sets how many vectors HNSW examines per shard before keeping the best k; raising it improves recall at some cost in speed. source_excludes drops the 384-number vector from responses, since only the text is needed downstream. Neither retriever alone is enough: BM25 misses paraphrases, and vector search can miss exact names and numbers.

Reciprocal rank fusion merges the lists

score = Σ 1 / (60 + rank)

Ranks, not raw scores. BM25 scores are unbounded and cosine sits between 0 and 1, so they can’t simply be added.

k = 60 keeps a single first place from outweighing agreement between both lists.

About 10 lines of Python, so it doesn’t depend on Elasticsearch version or license.

Illustrative example

ChunkBM25kNNRRF
French press120.0325
Grind size by brew method310.0323
Cold brew2not found0.0161

Cold brew ranks second for keywords but drops to third: only one retriever found it.

Each chunk gets one over sixty plus its rank in every list it appears in, and the scores are summed. A chunk that both retrievers agree on beats one that only a single retriever ranks highly. The table is a worked example of the arithmetic, not measured output. Elasticsearch also offers RRF as a built-in retriever in newer versions, with availability depending on version and license; doing it client-side keeps the project portable.

Generation: grounding the answer

Follow-up aware retrieval: the search query is the previous question plus the new one.

Numbered context: the top 5 chunks go in as [1] to [5].

System prompt rules: cite with [n], say when the guides don’t cover it, never invent specifics.

Short memory: the last 3 exchanges are sent as history.

The request sent to Claude

system: coffee-guide rules
messages: ...last 6 turns...
user:
  <guides>
  [1]
  How to Brew: Step-by-Step Methods
    - French press
  **You need:** coarse grind, about 1:15...
  [2] Grinding Coffee - Grind size...
  </guides>
  Question: How do I use a French press?

Retrieval quality sets the ceiling; the prompt makes sure the model stays under it. Numbering the passages lets the model cite precisely, and the same numbers map back to source sections in the web interface. Appending the previous question to the search query is a simple form of query rewriting: "what about for espresso?" on its own has little to retrieve against. History is capped at six messages to keep cost and latency flat as a conversation grows.

About 440 lines of Python across five scripts: common, ingest, search, ask and app.

Everything except the call to Claude runs locally. The API endpoint returns the answer text plus a list of numbered sources, which the page uses to render citation markers. Error handling maps the common failures, Elasticsearch unreachable, index missing, invalid API key, no credit, to plain-language messages with the fix.

Tuning: debug retrieval first

Run search.py on a bad answer’s question. Right section missing: a retrieval problem. Right section present: a prompt problem.

SettingCurrentRaising it
TOP_K chunks to Claude5More context, but more noise and cost
Hits per retriever20Deeper lists for fusion to work with
num_candidates100Better kNN recall, slower queries
Section boost2×Headings dominate keyword ranking more
RRF k60Flatter weighting across ranks
Chunk window / overlap250 / 50 wordsOnly affects sections over 250 words
Separating retrieval from generation is the most useful debugging habit in RAG. If the right chunk never reaches the prompt, no prompt change will fix it; look at chunking, boosts or the embedding model. If it does reach the prompt and the answer is still wrong, the problem is the instructions. Each setting here lives in .env or a function default, so it can be changed without touching the pipeline.

Technical next steps

Measure retrieval

Recall@5 and MRR on a labeled set of real questions, before tuning anything else.

Rerank

Score the top 20 fused hits with a cross-encoder, then keep the best 5.

Embed in the cluster

Elastic inference endpoints instead of a local Python model.

Native hybrid search

One request with Elasticsearch’s retriever API and built-in RRF, where licensed.

Metadata filters

Brew method or roast as keyword fields, filtering both retrievers.

Production hardening

Security and API keys, streamed responses, caching repeat questions.

Measuring comes first because every other change needs a number to show it helped. A small set of twenty to thirty questions, each labeled with the section that should be retrieved, gives recall at five and mean reciprocal rank. Reranking is usually the biggest single quality gain after hybrid search. Moving embedding and fusion into Elasticsearch simplifies the Python side but ties the project to a version and license that support those features.
